# The control plane

The operator application: a separate Laravel app at `control-plane/` that creates
and manages institutions. Institutions never reach it. For running it locally see
[Getting started](./getting-started.md); for the provisioning walkthrough see
[Operations](./operations.md).

---

## 1. What it is

The portal (`backend/`) runs one copy per institution. Something has to know which
institutions exist, hold their credentials, and create new ones. That is this app,
and it owns its own database.

**The rule everything follows from: a tenant container never holds control-plane
credentials.** Each tenant receives only its own database login, injected as
environment variables when its container starts. If tenant containers could reach
this database, one compromised institution would hold the keys to every other.

That is also why `platform_admin` is not a row in any tenant's `roles` table — an
Institution Admin has nothing to escalate into. `TenantBootstrapSeeder` refuses to
assign it and falls back to Coordinator.

## 2. Getting in

There is **no self-registration and no password reset.** Operator accounts are
created from the CLI only:

```bash
cd control-plane
php artisan platform:admin you@example.com --name="Your Name" --generate
```

| Option | Effect |
|---|---|
| `--generate` | Generates a 20-character password and prints it **once** |
| *(omitted)* | Prompts for one instead, minimum 12 characters |
| `--name=` | Display name; defaults to `Platform Operator` |

Prefer the prompt on a shared machine — it keeps the password out of shell
history. A lost operator password means creating a new account; there is no reset
flow.

## 3. The screens

Four, all server-rendered. Route model binding is by **slug**, so URLs read
`/tenants/tu`.

| Method | Path | Name | What it does |
|---|---|---|---|
| GET | `/login` | `login` | Operator sign-in |
| POST | `/login` | — | Authenticates (`throttle:10,1`) |
| POST | `/logout` | `logout` | Ends the session |
| GET | `/tenants` | `tenants.index` | List, with total/active/provisioning/failed counts |
| GET | `/tenants/new` | `tenants.create` | Add-institution form |
| POST | `/tenants` | `tenants.store` | Registers, then queues the pipeline |
| GET | `/tenants/{tenant:slug}` | `tenants.show` | Detail and live pipeline progress |
| POST | `/tenants/{tenant:slug}/retry` | `tenants.retry` | Resumes a failed pipeline |

`GET /` redirects to the list. Everything except `login` sits behind
`['auth', 'active']`. `/up` is the health endpoint.

**What is deliberately absent:** no suspend, delete or edit; no audit-log viewer;
no operator-management screen; **no JSON API**. Those are still CLI or manual —
see [What is not built](./operations.md#7-what-is-not-built).

## 4. The queue dependency

The likeliest operational surprise, so read this before using the form.

Submitting **Add institution** registers the tenant synchronously — the tenant
row, its domain and its generated credentials are all written during the request
— then queues `ProvisionTenantJob` for the slow half.

**A worker must be running or nothing progresses:**

```bash
cd control-plane
php artisan queue:work
```

Without one the form still succeeds and redirects you to the detail page, which
shows all six steps as *Waiting* and **auto-refreshes every five seconds
indefinitely, with no progress and no error.** Nothing warns you. If a tenant sits
at *Waiting* for more than a minute, check for a worker first.

The CLI path (`tenant:provision`) runs synchronously and needs no worker.

### The Coordinator's password

Generated by the bootstrap seeder and printed **once**, to whichever process runs
it. On the UI path that is the **queue worker's output**; on the CLI path it is
your terminal. It is never stored in plaintext and never rendered in the
interface.

Capture it, deliver it over a channel you trust, and have them change it at first
sign-in. If it is lost, use password reset on the tenant portal rather than
re-provisioning.

## 5. When a step fails

The pipeline stops, marks the tenant `failed`, and records the error against that
step. The detail page names the failed step, shows its error inline, and offers
**Retry provisioning** — which appears only when status is `failed`.

Every step is idempotent, so retrying resumes from the first step that has not
succeeded rather than starting over. `ProvisionTenantJob` sets `tries = 1`
deliberately: recovery is an operator decision made after reading the error, not a
blind requeue. Its `timeout` is 900 seconds.

## 6. Security behaviour

- **Lockout** — 5 failed attempts per email + IP, 15 minutes. The key prefix is
  **`cp-login:`**, not the tenant app's `login:`. A route throttle of 10/min sits
  in front, and a success clears the counter.
- **Deactivated operators cannot sign in** — `is_active` is folded into the
  credential query rather than checked after it.
- **Deactivation ends live sessions** — `EnsurePlatformAdminIsActive` re-checks
  every authenticated request, so revoking access takes effect immediately rather
  than whenever the session happens to expire.
- **Session fixation** — the session id is regenerated after a successful sign-in
  and invalidated on sign-out.
- **Credentials are never rendered.** Tenant database passwords and `APP_KEY`s go
  from the encrypted registry straight into the container. A test asserts they do
  not appear in the UI.
- CSRF protection on every form.
- **No per-action authorization.** Any active operator can do everything; the
  control plane has no roles of its own. Keep the account list short.

## 7. Audit

Every operator action lands in `control_plane_audit_logs` — append-only, with
actor, tenant, IP address and a JSON detail payload. The six action strings:

| Action | Recorded when |
|---|---|
| `login.succeeded` | Successful sign-in |
| `login.failed` | Bad credentials |
| `login.blocked` | Refused by the lockout |
| `logout` | Sign-out |
| `tenant.provision_requested` | Add-institution submitted |
| `tenant.provision_retried` | Retry pressed |

Auditing never breaks the action it observes: a failed write is reported, not
thrown.

> The **CLI path records nothing.** Auditing is wired into the web controllers
> only, so `tenant:provision` leaves no trail here. Use the UI when the record
> matters.

## 8. Naming an institution

The identifier becomes the subdomain, the database name and the container name, so
it is validated tightly and **cannot be changed afterwards**.

- 2–40 characters, lowercase letters, digits and hyphens
- must start with a letter and end with a letter or digit
- hyphens become underscores in the database name — `tu-pulchowk` becomes
  `tenant_tu_pulchowk`, because hyphens are legal in hostnames but not in Postgres
  identifiers

The form is forgiving about input: leaving the identifier blank derives one from
the institution name (`Tribhuvan University` becomes `tribhuvan-university`), and
input is always lowercased and trimmed rather than rejected for casing.

## 9. Configuration

Set in `control-plane/.env` before provisioning does anything real. Defaults live
in `control-plane/config/provisioning.php`.

| Variable | Default | Notes |
|---|---|---|
| `BASE_DOMAIN` | `supervisex.test` | Tenants are reached at `<slug>.<this>` |
| `POSTGRES_ADMIN_DSN` | **none** | Superuser DSN, used only to create databases and roles. **Never given to a tenant container.** |
| `TENANT_DB_HOST` | `postgres` | Where tenant databases are created |
| `TENANT_DB_PORT` | `5432` | |
| `TENANT_DB_DRIVER` | `pgsql` | |
| `TENANT_IMAGE_TAG` | `latest` | Pin this in production |
| `COMPOSE_FILE` | `../infra/compose.yaml` | Only if relocated |
| `PROVISION_HEALTH_ATTEMPTS` | `30` | Health-check budget… |
| `PROVISION_HEALTH_DELAY` | `2` | …30 × 2s is the "about a minute" the UI quotes |

Also required:

- **`APP_KEY` must exist** — it encrypts every tenant's database password and
  `APP_KEY`. Lose it and every stored credential becomes unreadable.
- `APP_URL` must move off `:8000`, which the tenant app also defaults to.
- `QUEUE_CONNECTION` must point at a real queue, with a worker running (§4).
- `SESSION_DRIVER=database` needs the sessions table migrated.

## 10. CLI equivalents

```bash
php artisan tenant:provision tu "Tribhuvan University" coordinator@tu.edu.np
php artisan tenant:list
```

`tenant:provision` runs the whole pipeline synchronously — no worker needed — and
re-running it resumes a failed tenant exactly as the Retry button does.
`tenant:list` prints slug, name, status, domain, image tag, schema version and
health.
