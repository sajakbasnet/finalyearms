# SupervisEx — Final Year Project Management Portal

React + Laravel 13 platform for managing the full FYP lifecycle — proposals,
supervision, progress, evaluation and final submission — built to serve **multiple
institutions**.

## Stack

- **Frontend:** React 19 (Vite + TypeScript), Tailwind v4, React Router
- **Backend:** Laravel 13, Sanctum (bearer tokens), SQLite locally / Postgres in production
- **Tenancy:** silo model — each institution gets **its own database and its own
  container**. No `tenant_id` columns; the container boundary *is* the tenant boundary.

## Repository layout

```
finalyearms/
├── backend/         Laravel API — ONE COPY RUNS PER INSTITUTION
├── frontend/        React SPA — one build serves every institution
├── control-plane/   Laravel app YOU run to create and manage institutions
├── infra/           Dockerfile, Caddy and Compose config
└── docs/            Documentation — start at docs/README.md
```

## Quick start

### Backend (the portal)

```bash
cd backend
composer setup    # install, .env, key, sqlite, migrate --seed
composer dev      # server + queue + logs, on :8000
```

### Frontend

```bash
cd frontend
npm install
npm run dev       # http://localhost:5173
```

Open <http://localhost:5173>.

### Control plane (only for tenant provisioning)

```bash
cd control-plane
composer install
php artisan migrate
php artisan platform:admin you@example.com --generate   # operator account
php artisan serve --port=8001
php artisan queue:work                                  # separate terminal
```

Sign in at <http://localhost:8001>. There is no self-registration — operator
accounts are created from the CLI only.

Full setup notes, including WSL specifics, in
[docs/getting-started.md](./docs/getting-started.md).

## Roles

Five roles are assignable inside an institution:

| Role | Reach |
|---|---|
| Institution Admin | Departments, academic calendar, user accounts, branding |
| Coordinator | Templates, teams, supervisor overrides, proposal oversight |
| Supervisor | Assigned projects |
| Student | Own project and team |
| Employer | Assigned internship *(role exists; no features yet)* |

Two more sit outside that table by design:

- **Platform Admin** lives in the control-plane database, never in a tenant — so
  an Institution Admin has nothing to escalate into.
- **Team Lead** is contextual, derived from `student_group_members.is_leader`, so
  a student can lead one team while remaining an ordinary member of another.

Authorization is permission-based (`can:<key>` against `config/rbac.php`), not
role-based. See [docs/architecture/access-model.md](./docs/architecture/access-model.md).

## API

Two APIs, documented separately because they have different audiences.

| API | Spec | Audience |
|---|---|---|
| Tenant portal — 88 operations | Generated by [Scramble](https://scramble.dedoc.co/); run the backend and open `/docs/api` | The SPA, internal |
| [Title registry](./docs/title-registry.md) — 3 operations | Hand-written: `control-plane/public/openapi.yaml`, served at `/openapi.yaml` | Other institutions, public |

The tenant spec is generated from `backend/routes/api.php`, so it tracks the
routes automatically. The registry spec is written by hand on purpose: it is a
public contract, and it should stay stable and readable regardless of how the
control plane happens to be implemented.

## Roadmap

Aligned with `studentportal.md` (the original v1.0 product specification, which
predates the multi-tenant work):

1. **Phase 1 — done.** Auth, roles, departments, teachers, students, supervisor
   assignment, dashboards
2. **Phase 2 — done.** Proposal submission, review, comments, versioning,
   notifications. Extended beyond the original spec with team formation,
   supervisor requests and [cross-institution duplicate checking](./docs/title-registry.md)
3. **Phase 3 — partial.** Progress reports and the academic calendar are built;
   applying an activity template to a live project is not, so milestones are
   not yet enforced against real work
4. **Phase 4 — partial.** `FinalSubmission` and `Evaluation` exist with
   endpoints; reporting does not
5. **Phase 5 — not started.** AI features and showcase

The gaps in phases 3 and 4 are listed per-area under "Not built" in each
relevant doc.
